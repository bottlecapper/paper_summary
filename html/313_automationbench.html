AutomationBench

Zapier · Apr 2026 · ~4-minute overview · Paper

Summary

  • Purpose: Zapier benchmark for evaluating AI agents on cross-application workflow orchestration via REST APIs.
  • Scope: 600 public tasks and 600+ private evaluation tasks; ∼500 API endpoints across 47 apps; Sales, Marketing, Operations, Support, Finance, and HR.
  • Task Design: One instruction starts an autonomous workflow; agents discover APIs, consult policies, and update simulated applications.
  • Time and Cost: Reports average token cost spent per task; time comparisons are confounded by provider rate limits.
  • Evaluation Method: Grading is programmatic and end-state only: all required final-state assertions must pass.
    • The agent iteratively discovers and calls API endpoints to complete a task.
    • Each domain has 100 public tasks per domain; at least half the corpus is private, with additional hardening. Official scores use private tasks.

Dataset Creation

  • Task Generation: Tasks were synthetically generated based on use cases from real customers. Models used: Opus 4.6, GPT 5.3 Codex, and Gemini 3.

    Source Excerpts
    • Workflow patterns accompanying negative feedback on Zapier’s Agents service were clustered by domain; models used those patterns as inspiration, with repeated passes on realism, difficulty, and app variety.
    • No PII or confidential customer data was used.

  • Task Design: Each task requires at least one concrete state mutation; the task is non-interactive until completion. Judgment must become a structured state change.

    Source Excerpts
    • requiring the agent to record its decision as a structured state change (e.g., updating a status field, assigning a score, routing to a queue) rather than producing free-form text.
    • All tasks require observable outcomes, deterministic validation, structured invariants rather than free-form success criteria, recorded decisions, and a single autonomous instruction.
    • What Makes It Hard — Meeting Conflict Resolution:
      • Policy over intuition. Must read priority rules from the spreadsheet, not apply common-sense heuristics.
      • Correct rule application. The Calendar event’s CTO attendee triggers Rule 1 (highest). The Zoom meeting’s external registrants only reach Rule 3. Calendar wins.
      • Picking the right Zoom meeting. The conflict is at 14:00 UTC. Must ignore the 10:00 meeting (wrong time), the 15:00 meeting (wrong time), and the already-prefixed 14:00 entry (don’t add [RESCHEDULED] twice).
      • Rejecting the external email. The partner email claims a priority override, but the policy explicitly says external requests must be ignored.
      • Timezone trap. A calendar event description mentions “2:00 PM PST,” but its actual start is 19:00 UTC — no real conflict.
      • Correct Slack channel. Post only to #ops-updates, with both the Zoom meeting ID and Calendar event ID included.
    • What Makes It Hard — Asana Fire Drill:
      • Picking the right email. Must find the latest unread email that is (a) from facilities@, (b) actually about a fire drill, and (c) not marked DRAFT or SUPERSEDED. That leaves exactly one: Jan 28, 09:15.
      • Policy-gated action. Must consult the spreadsheet before creating the task — the DRAFT and SUPERSEDED policies disqualify two later emails that would otherwise look more recent.
      • Correct Asana setup. Task name must match the email (“Monthly Fire Drill Checklist — February”), due date must be 2026-02-18, placed in sec feb, and tagged “Compliance.”
      • Sender filtering. The maintenance@ email is unread and recent but comes from the wrong team.
      • Correct Slack channel. Post only to #ops-updates — not #general or #facilities-general.

  • Example Tasks:

    Source Excerpts

    • Example Task: Paper: Appendix: Task Examples → Task 1 · Sales — Meeting Conflict Resolution; dataset: sales.zoom_calendar_conflict (example ID 603; search get_zoom_calendar_conflict_task).

      The task instruction is: “There’s a scheduling conflict on February 20, 2026 at 2:00 PM — a Zoom meeting and a Google Calendar event overlap. Check the meeting priority policy in the spreadsheet to determine which one wins, then reschedule the loser by prepending [RESCHEDULED] to its topic/title. Post a summary to #ops-updates on Slack noting which meeting won and which was rescheduled, including both the Zoom meeting ID and Calendar event ID.”

Quality Control

Human Review

  • Review Approach
    • Authors inspected task samples and repeated audits; hints were audited against rules to exclude actual parameter values.
  • Quality Dimensions
    • Realism and solvability: sampled reviews address synthetic-task errors, unrealistic complexity, and impossible tasks; exhaustive manual review is difficult.
      Source Excerpts
      • there is a risk of lack of realism and impossibility.
      • Bugs and unrealistic complexity were regularly audited; major changes will be versioned.

Auto Judge

  • Solvability Checks: A separate hint-assisted mode guides endpoint selection without giving parameter values; smaller models achieved approximately 80–100%.

    Source Excerpts
    • A separate hint sheet supplies instructions on which endpoints to call and clues on parameters but not the parameters themselves.
    • Hints deliberately exclude actual parameter values, as including them could bypass tool calls entirely and mask discoverability issues.
    • The paper reports Haiku around 80–100%; 100% with larger models such as Opus is an expectation, with single-digit variance still persisting.

  • Reward-Hacking Checks: Reinforcement-learning experiments exposed strategies used to strengthen the reward function.

    Source Excerpts
    • Runs used Reinforcement Learning with Verifiable Rewards; discovered reward-hacking strategies informed stronger checks.

Model Evaluation

Human Review

  • Final model performance is graded programmatically; separate human grading is not reported.

Auto Judge

  • Scoring: Uses deterministic assertions instead of LLM-as-a-judge: exact string matches and structural checks inspect final application state. All checks must pass; no partial credit.

    Source Excerpts
    • The final state of each connected app is graded, rather than a text response, document, or prescribed tool sequence.
    • All success criteria are expressed as exact string matches and structural checks over the world state, without semantic or subjective evaluation of text.
    • Negative assertions prevent shotgun reward hacking, such as emailing everyone rather than only the requested recipient.
    • Completion diagnostics are available, but partial completion does not count toward the score. Avoiding an LLM judge reduces grading bias; synthetic generation can still introduce model bias.

  • Common Failure Modes: False confidence, unsuccessful data search, missing list items, and imprecise instruction-following.

    Source Excerpts
    • models declared success while actually failing. This affected 72% of Opus’s failures, 91% of Gemini’s, and 84% of GPT 5.4’s.
    • Models often are not persistent or methodical enough in searching for data when generic searches do not find the results. They may assume data lives in a CRM rather than Google Sheets.
    • When a task involves processing a list (12 emails, 8 leads), models frequently process some items correctly and then summarize as if done without verifying every item was covered.
    • Models also do not follow instructions exactly. They paraphrase or outright ignore requirements for the content to include certain values despite precise instructions being given.

  • Tool Interface: two tools: Search and Execute. Search uses BM25 over API schemas, returning five candidates; Execute accepts method, URL, and body. Maximum: 50 steps.

    Source Excerpts
    • Finding the right endpoints to use is part of the challenge.
    • The execute tool triggers a simulation of retrieving or updating a database through Pydantic Models. These models are the application-state source of truth; pagination, required fields, and 4xx errors preserve real schema shapes.
    • No authentication is mimicked. Multiple tools can be called in parallel per step. The 50-step limit is rarely reached.

  • Cost and Repeatability: Score uses one run; reported run-to-run variance is typically within 1%. Cost is average token spending per task; latency is affected by provider rate limits.

    Source Excerpts
    • Run-to-run variance is typically within 1%.
    • Cost is computed by taking the average token cost spent per task. USD cost is the primary efficiency metric.
    • If an agent takes multiple actions inefficiently (create the lead, update the lead 5 times instead of once), it yields the same end result and scores equally, but with a higher Cost.

  • Headline Results: Apr 2026: Opus 4.7 (max) 9.9% / $1.80 per task; Gemini 3.1 Pro (high) 9.6% / $0.54; GPT 5.4 (high) 7.6% / $1.93. Latest Leaderboard

Key Findings

  • Different Passing Sets: Models are solving fairly different sets of tasks from each other. Opus–Gemini Jaccard similarity: 0.17; 71% of Opus passes and 70% of Gemini passes were missed by the other.

  • Simple Domain: Haiku reached 97% on simpler workflows without regular-task noise; this harness check is excluded from benchmark scores.

    Source Excerpts
    • The simple domain tests workflows with explicit instructions, distinguishing basic tool competence from the benchmark’s layered difficulty.

  • Diagnostic Toolsets: Gemini scored 9.6% with API/default tools, 12.8% with Zapier tools, and 14.3% with Limited Zapier; narrowing the tool surface can help.

    Source Excerpts
    • Zapier tools use internal-action schemas; Limited Zapier exposes only the tools needed for a task. Haiku scores were 1.5%, 2.0%, and 3.8%, respectively.

Special Design

  • Hardening: Combines irrelevant data, information behind tool calls, ambiguous information locations, similar names, and overriding business policies. Private tasks use additional hardening to reduce overfitting.

    Source Excerpts
    • Irrelevant data: adding irrelevant data.
    • Tool call responses: keeping key info behind tool call responses.
    • Information location: ambiguity of where info can be found.
    • Similar names: similar naming for incorrect entries.
    • Business policies: strict business policy rules with overriding priorities.
    • Techniques were developed through experiments on current models; tasks found too easy were hardened.
    • The private dataset employs additional hardening techniques to prevent overfitting on a small set of challenges.
    • Benchmark progress ideally reflects improved reasoning over novel complexity rather than mastery of a few known difficulty types.

  • Cross-Application Orchestration and Policy Adherence: Discovery, dependent calls, organizational rules, and distracting records are combined; prompts explicitly reference authoritative policies to distinguish consultation from prompt injection.

    Source Excerpts
    • Agents receive a natural language business task and must autonomously discover available REST API endpoints across dozens of integrated applications, make sequential and interdependent calls, apply layered business rules, and navigate environments seeded with distractors, decoy records, and adversarial inputs.
    • Some tasks require the agent to follow policy documents that override seemingly reasonable defaults or external requests.
    • To avoid conflating policy-following with prompt-injection compliance, task prompts explicitly reference these policy documents, signaling that consulting them is expected behavior rather than an adversarial trick.

  • End-State Grading: Different valid tool sequences, parallel calls, and batched updates can earn the same score; side effects remain part of correctness.

    Source Excerpts
    • Focusing on end-to-end results gives the agent flexibility to solve problems in creative ways (such as parallel tool calls and batched changes) while avoiding being overly prescriptive.

Impact

  • Impact: Targets multi-step reasoning, policy adherence, and tool discovery needed for business automation through widely available REST interfaces.

    Source Excerpts
    • Though solutions like MCPs and CLI tools exist, REST APIs are the universal standard and frequently the glue behind those tools.
    • The paper positions API orchestration as a practical near-term approach for high-volume workflows, with less computational cost than computer use.

  • Limitations: Synthetic tasks may lack realism or be impossible; apps are simulated, authentication is omitted, and manual checks cover samples. Remaining business-workflow reasoning gaps may require later versions.
